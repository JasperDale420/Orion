## P0 — Self-inflicted Gateway 429 storm from the stale-entry-cancel retry loop

**Files:** `src/orion/execution/execution_engine.py` (`_cancel_stale_entry_orders` 1934–1998;
order-poll driver 2327–2406; `_ORDER_POLL_MIN_INTERVAL_SECONDS = 5.0` @2268),
`src/orion/clients/gateway_trading_client.py` (`_request` 67–110, `cancel_order` 279–281),
`src/orion/execution/rate_limiter.py` (only used @execution_engine.py:1095).

**Mechanism (root cause):**
1. Every **5 s** the order-poll loop calls `_cancel_stale_entry_orders`, which fetches all
   unfilled `orion_`-prefixed entry orders older than 180 s and issues one `cancel_order` each.
2. On a **rejected** cancel — `{"error": ...}` returned for HTTP 429 (`GW-E4001`) **or** the
   permanent `GW-E2009 "Trading capability required"` — the code logs `STALE_ENTRY_CANCEL_REJECTED`
   and `continue`s **without flipping the DB row out of `open_states`** (the optimistic flip at
   1976–1982 runs only on a *successful* cancel). So the same order is re-fetched and re-cancelled
   every 5 s, indefinitely (until expiry/fill).
3. `gateway_trading_client._request` has **no 429 / `Retry-After` handling and no backoff** — it
   logs `gateway_trading_http_error` and returns the error.
4. Cancels + status-polls **bypass `OrderRateLimiter`** (it gates only new submissions @1095; its
   200/min ceiling is also the *whole shared Alpaca account*, not Orion's share).
5. Feedback loop: a few un-cancellable orders → re-cancel-all every 5 s → exceeds the shared
   gateway limit → 429s → cancels keep failing → never flipped → storm sustains itself. The same
   gateway serves clock/positions/quotes, so **execution goes degraded**, UW connectors
   retry-exhaust, and pipeline stages go stale → deadman pages Discord. (703 retries/order ≈ a
   full session at 5 s cadence.)

**Fix direction (review me):**
- **Bound retries on rejection.** Track per-order cancel attempts + last-attempt time. Classify the
  rejection: **transient** (429/5xx) → exponential backoff, capped attempts; **permanent**
  (`GW-E2009`, intent/4xx) → stop retrying, alert once, do not re-enqueue every cycle.
- **Honor 429 / cooldown the gateway client.** On `GW-E4001`/429 respect `Retry-After` and set a
  short module-level "gateway cooldown until T" gate checked before trading calls, so the whole
  loop stops hammering during a rate-limit window.
- **Rate-gate the sweep.** Route cancels/polls through the limiter (or a dedicated budget) and cap
  cancels-per-cycle (K) so the sweep can't blow the shared-account limit.
- Preserve existing on-success optimistic flip.

**Verify:** unit test — `cancel_order` returning an error N times ⇒ the order is NOT re-attempted
every cycle (attempt count bounded); a 429 ⇒ cooldown engaged; a `GW-E2009` ⇒ retried at most once.

## Codex adversarial review (gpt-5.5, xhigh) — verdict: SOUND-WITH-CHANGES

Verified against code by Claude. Confirmed additions that the plan MUST absorb:

- **[VERIFIED, safety-critical] 429 is treated as a CONFIRMED close rejection → native flatten.**
  `classify_close_failure` returns `confirmed_rejection` for any 4xx (execution_engine.py:91-93);
  a failed close then escalates to a **native flatten** (1728-1738). Native closes are NOT
  orion-attributed → the daily-loss/drawdown kill switch goes blind (see memory
  `project_native_close_not_attributed`). During a 429 storm, exits silently route to unattributed
  native closes. **Fix:** treat 429 (and 5xx) as TRANSIENT in `classify_close_failure` → back off
  and retry the limit; never escalate to native purely because of a rate-limit 429.

- **[VERIFIED] Bracket stop-loss is a guaranteed TypeError on the real client.**
  `_place_bracket_orders` calls `create_order(order_type="stop", stop_price=…)`
  (execution_engine.py:1326-1335, 1345) but `GatewayTradingClient.create_order` has no `stop_price`
  param (gateway_trading_client.py:154-190) — it's the only `create_order` in `src/`. So real-client
  stop placement always raises → swallowed as `bracket_stop_loss_failed` (1350-1352) → **positions
  carry no broker-side protective stop.** Introduced in refactor `92d364bf`. June log successes are
  test-fixture-only (`AAPL260418C00150000`, mock client). **Action: confirm whether live config
  places brackets; if so this is its own P0 (add `stop_price` to the Gateway client / verify Gateway
  supports options stops — Alpaca historically does not, in which case brackets must be redesigned).**

- **[VERIFIED] Cancel give-up must NOT silently strand a real working order.** Bounding retries is
  required, but never mark an order `canceled` locally on give-up — record `pending_cancel` /
  `manual_review` state + alert, reconcile against broker truth.

- **[VERIFIED] Optimistic flip is too eager.** The on-success flip writes DB `canceled` after ANY
  no-error response (1975-1982), not a broker-confirmed terminal. A late fill on an order Orion
  thinks is dead is a shared-account hazard. Prefer `pending_cancel` + reconcile to broker terminal.

- **[VERIFIED] `get_orders(status="all", limit=200)` window leaves stale local-open rows.**
  Terminal broker orders outside the 200-row poll window (execution_engine.py:2335) never reconcile
  to terminal locally, so the sweep keeps re-cancelling them — a direct storm amplifier the plan
  under-specified. **Fix:** reconcile stale DB-open rows by direct `get_order(id)` rather than
  re-cancelling blind.

- **[VERIFIED] Other un-gated cancel paths.** Close-path `_cancel_resting_orion_orders`
  (`get_orders(status="open", limit=500)` + per-order `cancel_order`, ~1857/1877) also bypasses the
  limiter. Any rate-gating must cover this path too.

- **[VALID] Module-level cooldown is process-local.** It stops Orion hammering itself (which IS the
  cause of Orion's self-inflicted storm) but does NOT protect the shared account from sibling systems.
  Account-level coordination, if wanted, belongs in Data-Gateway/Redis — out of scope for the Orion
  fix; note as a follow-up.

- **[VALID] Budget priority lanes.** Emergency exits must take precedence over opening orders, which
  take precedence over stale-cancel sweeps. A cooldown/limiter must reserve an exit lane so it can
  never block an emergency close.

- **[VALID] Partial-fill remainder.** The sweep excludes `partially_filled` (1917); the unfilled
  remainder can reserve DTBP indefinitely with no handler. Track as follow-up.

- **[VALID] P1 edge cases.** `evaluate_stage_freshness` silently treats tz-naive `max_ts` as UTC
  (182-183) — could mask a local-time data bug. Also TRACE & REMOVE the future-dated BronzeEvent
  rows (likely a direct/backfill/test writer; persistence preserves a supplied `received_ts_utc`),
  not merely alert on them.

### Revised must-fix set before implementation
1. P0 cancel loop: per-order cancel state (attempts/last/next-eligible/last-code), transient-vs-permanent
   classification, capped retries with backoff+jitter, per-cycle cap, give-up → `pending_cancel`+alert
   (never silent local-cancel).
2. Treat 429/5xx as transient in `classify_close_failure` (stop native-escalation on rate-limit).
3. Reserve an emergency-exit lane in any cooldown/rate gate; cover close-path cancels too.
4. Reconcile stale DB-open rows via `get_order(id)`, not blind re-cancel (200-row window fix).
5. P1: future-timestamp guard + test; trace/remove the bad BronzeEvent rows.
6. Confirm bracket/stop-loss live impact; if live, fix `stop_price` path as its own P0.

### Bracket stop-loss investigation outcome (2026-06-16)
- **DORMANT in production.** `enable_bracket_orders` defaults `False` (config.py:67) and is NOT
  overridden in `.env`; the call is gated at execution_engine.py:1220. All 472 bracket log lines are
  the test fixture `AAPL260418C00150000` (mock client) — **zero real tickers**. Protection runs via
  PositionMonitor software exits, not broker brackets. So this defect is NOT causing the alerts and
  is NOT live.
- The TypeError is real, but a real fix needs a **design decision**: Alpaca does not support `stop`
  order types on options, so adding `stop_price` to the Gateway client would just convert the
  TypeError into a broker 422. Options brackets would need synthetic stops or to stay on the
  PositionMonitor.
- **Action: descoped from this remediation round.** Minimum: ensure the path fails loud / is guarded
  so nobody flips `enable_bracket_orders=True` and silently gets unprotected positions. Full redesign
  is a separate decision.
